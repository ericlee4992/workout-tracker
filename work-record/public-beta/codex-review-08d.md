## Standards

1. **P2 — Download cleanup does not enforce its promised deadline.** **Locations:** `server/scripts/feedback.mjs:60–78`; `server/src/pages.ts:109–110,129–132`; `server/README.md:152–154`. D61 promises downloaded copies disappear within 30 days or when the feedback disappears. Cleanup runs only at the start of a subsequent production `list`, `show`, `screenshot` or `delete` command. Download a screenshot and stop running the tool: the file can remain indefinitely, including after its sender deletes their account. There is no scheduled cleanup or written requirement to run it by a deadline. Moreover, the live-key query precedes age pruning, so a database failure also prevents removal of already expired files. **Suggested correction:** provide a scheduled/monitored cleanup or a concrete operating procedure that meets the chosen deadline and handles account/individual deletions. Prune age-expired files independently of database availability; preserve unexpired files when liveness cannot be established. Add isolated CLI tests covering no subsequent interactive use, expiry, deleted feedback and query failure. Changing the promise instead requires explicitly revisiting D61.

2. **P2 — The restore procedure can resurrect deleted data and expose it before reconciliation.** **Locations:** `server/README.md:114–137`; `server/src/pages.ts:136–138`. D61 and the page promise to remove everything deleted since the backup **before** using restored data. The procedure compares only `accounts` and `feedback` IDs. A surviving account's cleared training profile (`server/src/training.ts:79`), deleted session (`server/src/store.ts:111–112`) and expired AI rows are not covered; clearing optional measurements within an existing profile also survives neither an ID comparison nor the proposed account cleanup. Separately, the documented Time Travel command overwrites the currently bound database in place. There is no maintenance isolation, preservation of the latest deletion evidence before replacement, or verification gate before requests/cron resume. [Cloudflare's Time Travel documentation](https://developers.cloudflare.com/d1/reference/time-travel/) confirms the in-place overwrite. **Suggested correction:** specify an ordered procedure that isolates traffic and scheduled work, preserves trustworthy current deletion/clearing evidence before restore, reconciles all affected tables and cleared fields, reapplies retention and pending cleanup, verifies the result, and only then resumes service. If adequate evidence cannot be recovered, fail closed rather than assert the promise was met. The explicit 30-day manual-export deletion instruction and restrictive file permissions are otherwise present.

3. **P3 — `--local` and production share the download directory.** **Locations:** `server/scripts/feedback.mjs:28–29,60–72,105–123`. The flag correctly selects local D1/R2, but both environments write to `server/.feedback`. The next production invocation removes local downloads because their keys are absent from production. With a copied/reused feedback key, local screenshot download/delete can overwrite/remove a production download. **Suggested correction:** separate local and production download directories and scope pruning/deletion accordingly; test environment isolation. The production delete sequence itself is sensible: R2 first, downloaded file second, database row last. A failure before the final database delete leaves the row for retry; no false success is printed. The script was inspected, not executed against either environment.

## Spec

4. **P2 — Clearing a training profile is promised but not reachable in the app.** **Locations:** `server/src/pages.ts:75–77`; `WorkoutTracker/Features/Account/ProfileView.swift:69–120`; `WorkoutTracker/Features/Account/TrainingProfileEditor.swift:9,24,46–48,80–84`. The page says users can change or clear their training profile. The UI provides Edit/Set Up, and the editor saves only a nonoptional valid profile. The production callers at `ProfileSample.swift:72–76` and `AIRoutineSheet.swift:213` never send `nil`. The server's `training: null` operation and the optional `AccountStore.saveTraining` parameter therefore do not deliver a user-accessible clearing action. This violates ticket 08's requirement that published behavior match the app. **Suggested correction:** expose and verify an explicit clear-training-profile action, including its actual server request and resulting empty state, or revise the page to describe editing and removal through account deletion without promising independent clearing.

5. **P2 — Signing out does not necessarily remove the server session record.** **Locations:** `server/src/pages.ts:72–74`; `WorkoutTracker/Features/Account/AccountStore.swift:298–305`; `server/src/store.ts:83–98`; `server/src/index.ts:204–207`. The page unconditionally says the session record is removed when the user signs out. The app forgets the token first and suppresses failure of the sign-out request. Signing out offline therefore leaves the account-linked session row behind; inactivity expires its authorization, but the server removes an expired row only if that forgotten token is presented again. The hourly tasks do not prune sessions, so the record can persist until account deletion. This draft-era statement needs qualification against the now-wired app. **Suggested correction:** say that server-side sign-out removal happens when the request reaches the server and accurately state residual record retention, or implement reliable removal/expiry cleanup and update the policy to that tested behavior.

6. **P2 — The support page overpromises account deletion.** **Location:** `server/src/pages.ts:168–169`. “Everything my server holds about you” contradicts both the detailed privacy page and the implementation. Signed-out feedback that identifies the same person remains (`server/src/store.ts:158` deletes only feedback with that account ID); encrypted revocation credentials can remain pending retry; recovery history and exports retain copies. A general link to the policy does not make this absolute instruction true. **Suggested correction:** say Delete Account removes the account and its linked data from the live database, and point directly to the retention/revocation exceptions and the separate email route for signed-out feedback.

7. **P3 — The deletion directions name a “Profile” destination that has no matching visible label.** **Locations:** `server/src/pages.ts:129,168–169`; `WorkoutTracker/Features/Settings/SettingsView.swift:43–51`; `WorkoutTracker/Features/Account/ProfileView.swift:25,35–40,179–226`. The actual entry is the name/email card at the top of Settings, and its destination is titled with the user's name. There is no row/tab titled “Profile”; the delete row is “Delete Account…” and its confirmation is “Delete Account.” The user explicitly required the named paths to match labels. **Suggested correction:** use “Settings → your name/email at the top → Delete Account…” on both pages. Send Feedback and Ask AI match their Settings labels; Export exists as the labeled Settings section containing the export card.

## Verification and remaining release gates

- **Feedback expiry:** `sweepFeedback` uses the same `created_at < cutoff ORDER BY created_at, id LIMIT 1000` selection in both statements. The first changes only `screenshot_deletions`, so it does not change the feedback row set selected by the second. Both execute in a single D1 batch; [D1 documents batch transaction rollback](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). Account deletion uses its own transaction, and queue IDs protect requeued jobs from an older sweep. R2 failure retains the queued key for retry. No expiry correctness/atomicity defect found.
- **Coverage/budget:** tests exercise the exact 365-day boundary, newer rows, rows with/without screenshots, failed R2 deletion and retry, 1,001-row batching, account-deletion cleanup and queue interleavings. The bound is **14 feedback statements + 21 revocation statements + 2 AI-prune statements = 37**, below [D1 Free's 50 queries per invocation](https://developers.cloudflare.com/d1/platform/limits/); deletes bind at most 100 IDs. The new expiry tests do not inject failure of the second transaction statement or test timestamp ties at the batch boundary, and the CLI changes have no tests. These are useful regression additions, not evidence the transaction is broken. One year is implemented as 365 days, followed by the successful hourly sweep; backlogs or R2 failure can delay screenshot removal. Wording should describe that scheduled cleanup/retry behavior rather than an exact anniversary erasure.
- **Observability:** [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) documents `logs.invocation_logs: false` as disabling the enriched request/response invocation record; [tracing configuration](https://developers.cloudflare.com/workers/observability/traces/) supports explicitly disabling traces. Thus the configuration addresses the identified stored IP/location/header paths. Free log retention is currently three days. This is configuration/documentation evidence, not a post-deployment observation or a promise about Cloudflare's own infrastructure processing. It also does not erase previously stored invocation logs; let their retention run out or account for them during rollout. Workers Logs still supports runtime errors/uncaught exceptions and platform metadata, so “only lines my server writes” is better phrased as application diagnostic logs with invocation logging/tracing disabled. Every `console.*` call in `server/src` was inspected: none explicitly logs IP, account ID, email, body, AI photo/input/output or headers. Logged values are fixed route/flow, outcome, numeric counts/timing and error names. The local feedback-reading CLI intentionally prints feedback/identity to its terminal; that is distinct from Worker logs.
