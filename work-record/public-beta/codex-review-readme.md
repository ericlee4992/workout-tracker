## Standards

1. **P2 — The build prerequisite does not acknowledge the known Xcode 26 failure.** **Location:** `README.md:60`. “Requires Xcode 26 or later” presents Xcode 26 as a supported working toolchain, but current `docs/STATE.md:132–134` records an unresolved compilation failure in `LiveSetRow.swift` on the Xcode 26 CI runner and successful local builds with Xcode 27. This does not establish that every Xcode 26 installation fails, but it does make the unconditional compatibility claim unsupported by current evidence. **Suggested correction:** identify Xcode 27 as the verified toolchain and mention/link the unresolved Xcode 26 runner/SDK compatibility issue; do not imply a successful Xcode 26 check occurred during this documentation refresh.

2. **P3 — The public unit-test command depends on an unexplained local simulator and is already recorded as failing by name.** **Location:** `README.md:71–73`. `WT-iPhone` is a developer-created simulator, not something a fresh checkout provides. More concretely, ticket 08's README evidence (`work-record/public-beta/issues/08-external-testers.md:210–211`) says this name resolved against the latest runtime and failed because the existing simulator used a different runtime. `docs/DEVELOPMENT.md:66–69` explains inspecting/creating/selecting a simulator, but the README gives no such prerequisite or substitution. **Suggested correction:** instruct readers to choose an available simulator and substitute its UDID in `-destination 'platform=iOS Simulator,id=<UDID>'`, or link the simulator setup steps and supply an explicit compatible runtime. Avoid publishing the developer's UDID as a universal destination.

3. **P3 — The public layout presents a local generated cache as checked-in repository content.** **Location:** `README.md:93`. `graft/` exists in this checkout but is excluded by `.gitignore:49`; `git ls-files graft` returns no files. A GitHub reader or fresh clone will not find the listed directory. **Suggested correction:** mark it explicitly as a locally generated, gitignored cache created by `graft build`, or omit it from the repository layout table.

4. **P3 — The Watch folder description understates what the source contains.** **Location:** `README.md:87`. “A placeholder Watch target” is not an accurate description of `WorkoutTrackerWatch/WatchWorkoutModel.swift` and `WatchRootView.swift`: they implement a HealthKit workout session, heart-rate collection, WatchConnectivity messages and a live reading/rest display. The separate claim that it has never been built or run is supported by current project records. **Suggested correction:** describe it as an implemented but unverified Watch companion, not embedded in the beta. This source-layout correction is separate from the shipping-feature claim in finding 6.

## Spec

5. **P2 — The overview incorrectly applies fallback history to prefilled inputs.** **Location:** `README.md:12–15`. The sentence groups “prefilled sets” with machine → equipment model → exercise fallback. `docs/SPEC.md:44` explicitly limits prefill to matching equipment history; fallback layers are reference display only. `WorkoutTracker/Domain/PreviousPerformance.swift:103–120` obtains prefill through `layerOneMatch`, and `WorkoutTrackerTests/PreviousPerformanceTests.swift:195–212` specifically asserts no prefill for a new machine despite available same-model fallback history. **Suggested correction:** separate the claims: comparison history/records have labeled layers, while prefill uses only the matching machine/equipment context. Also qualify line 12's “every set” to machine-based sets: free-weight and machineless entries are supported (`docs/SPEC.md:33`), so not every set requires a particular machine and gym.

6. **P2 — Apple Watch live heart rate is advertised as a beta feature although its required companion is not included.** **Location:** `README.md:41–42`. `work-record/public-beta/spec.md:234–235` explicitly excludes embedding the Watch companion in this beta. The phone target's build phases/dependencies (`WorkoutTracker.xcodeproj/project.pbxproj:255–275`) do not embed it, and `WorkoutTracker/Domain/WatchHeartRateProvider.swift:6–9,59–67` explains that live Watch readings require the app on the wrist. Source for a receiver is not evidence of a usable shipping Watch feature. **Suggested correction:** advertise supported phone-connected heart-rate sensors, qualifying the AirPods model where appropriate, and clearly label Watch support as not included/unverified rather than listing it among current beta capabilities.

7. **P2 — “CSV or JSON export of everything” overpromises the export's contents.** **Location:** `README.md:43–44`. `WorkoutTracker/Domain/ExportCSV.swift:12–17` explicitly defines CSV as a ledger of strength sets and cardio segments, omitting objects with neither. Heart-rate series and routes belong to the fuller JSON export; the snapshot does not export server account/training-profile records or every application setting. The approved policy already distinguishes these formats (`server/src/pages.ts`, “Your exports”). **Suggested correction:** say workout data can be exported as JSON or CSV, identifying JSON as the fullest workout record and CSV as a table of sets/cardio. Remove “everything.”

8. **P3 — The privacy summary turns no automatic upload into an absolute nonreceipt guarantee.** **Location:** `README.md:53`. “The server never receives them” omits intentional submissions: users can include workout information in feedback text or screenshots, which the app sends to the server (`WorkoutTracker/Domain/FeedbackClient.swift:19–40`). The approved policy explains voluntary feedback/screenshot/export exceptions (`server/src/pages.ts:33–41`). **Suggested correction:** say workout history is stored locally and is not automatically uploaded, then distinguish information the user deliberately sends through AI or feedback. Keep the full policy link.
