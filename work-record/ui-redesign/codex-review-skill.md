# T6 — ios-design skill review

Reviewed `main..HEAD` on `ios-design-skill` (`9b5b639..2636dfa`), limited to the three skill documents and the CLAUDE.md pointer. Inspection only, including existing Start capture, implementation, assets, prior reviews and Apple's current HIG JSON. No `xcodebuild` or `simctl`; no reviewed files changed. **Not clear: medium-severity rule and verification defects; no high-severity findings.**

1. **P2 — The capture gate does not establish the coverage it claims.** `.claude/skills/ios-design/REFERENCE.md:101` describes default/AccessibilityL coverage per screen, but `RedesignScreenshotUITests.swift:125` captures Settings only at default; calendar, chart and several sheets also lack paired coverage. Start's default fixture (`:88`) shows a resumed workout, while its AXL fixture (`:101`) shows templates, so these are different states. The helper (`:21`) replaces application launch arguments; the AXL argument must reach each app launch, not merely the test runner. `SKILL.md:51` needs a named screen/state/size matrix, matching fixtures with representative long content, and captures after scrolling where necessary. Require extending missing fixtures and inspecting captures from the final revision before declaring every string whole. Also, `REFERENCE.md:23` conflates AXL with the largest size: AccessibilityL is the first accessibility category; AX5/accessibilityExtraExtraExtraLarge is the largest. Either explicitly retain AXL as this project's limited gate or add the actual maximum; do not claim maximum-size coverage from AXL. [Apple typography](https://developer.apple.com/design/human-interface-guidelines/typography).

2. **P2 — One accent colour has become one coloured object.** `.claude/skills/ios-design/SKILL.md:60` requires everything besides the hero to be ink/grey/white and declares two amber things competing. That rejects the system it mandates: `RootView.swift` tints the selected tab amber; `Chip.swift` uses amber for selection; completed sets and progress also use it. A selected tab plus a primary action already fails. The same paragraph contradicts the muscle/warmup exceptions in the brief. `SKILL.md:71` and `REVIEW.md:17` additionally omit valid semantic uses: failure sets use `Theme.danger`, drop sets use `Theme.drop`, and unit chips have their own colours (`ExerciseEntryCard.swift:21`, `Theme.swift`). Define one dominant treatment **per screen state**, while retaining named selection, navigation, completion and domain-status uses. Dominance cannot be checked by counting amber occurrences.

3. **P2 — Type rules reject the prescribed tokens.** `.claude/skills/ios-design/SKILL.md:69` restricts weights to Regular–Bold, but `Theme.hero` is Black; `REFERENCE.md:89` correctly records that. The restriction of Rounded to existing numerals also conflicts with that row's permission to use `hero` for a title. Separately, `REVIEW.md:15` permits a title style only once, while item 4 requires every glanceable figure to use `stat` or `hero`; `stat` is Title 2, so a normal multi-stat summary fails. Explicitly allow the hero token and distinguish one screen heading from repeated numeric text styles.

4. **P2 — The sheet check forces copy and behaviour changes.** `.claude/skills/ios-design/REVIEW.md:22` requires Cancel + Done on every sheet. Existing valid cases include the calendar's Close (`HistoryCalendarSheet.swift:48`), Previous Performance's dismiss-only Done (`PreviousPerformanceSheet.swift:39`), and the rest editor's Cancel + Save (`ExerciseRestSettingsSheet.swift:37`). Adding or renaming buttons would violate the frozen-copy/behaviour scope. Apple's guidance distinguishes dismissal, committing edits and moving back; it does not require every sheet to contain that literal pair. Classify the task and preserve its existing commit/dismiss semantics. Likewise, `REFERENCE.md:61` should not turn Apple's advice to consider alternatives for complex/prolonged flows into a ban on all multi-step sheets. [Apple sheets](https://developer.apple.com/design/human-interface-guidelines/sheets).

5. **P2 — Correct Apple guidance conflicts with the locked appearance decision.** `.claude/skills/ios-design/REFERENCE.md:66` accurately reflects Apple's current requirement for light/dark custom-colour variants even in a single-appearance app, for Liquid Glass adaptivity. However, D54 (`docs/DECISIONS.md:63`) explicitly says Any appearance only, no light variant by decision. Saying the app forces dark does not resolve this conflict. Name the D54 exception and its limitation, or explicitly propose reopening D54; do not leave the implementing agent to choose between two mandatory instructions. [Apple colour](https://developer.apple.com/design/human-interface-guidelines/color).

6. **P2 — Contrast recommendations become an incompatible hard pass threshold.** `.claude/skills/ios-design/REFERENCE.md:68`, `SKILL.md:74` and `REVIEW.md:18` make 7:1 mandatory for small text/custom pairs. Apple's Dark Mode guidance says to strive for 7:1, especially for small text; it is not the stated minimum. Using the actual sRGB assets, `TextTertiary` is approximately 5.36:1 on Background, 4.76:1 on Card, 4.09:1 on Elevated and 3.56:1 on Fill. Thus the reference's general “text on ink” use is not an approved-pair contract, and even its darker surfaces cannot satisfy the new small-text rule. Distinguish the minimum from the stronger target, name safe foreground/background combinations, and identify any intentional policy increase as a token change. Define what “small” means and how ratios are measured; a screenshot alone cannot prove the numeric check. [Apple Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode), [Apple accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility).

7. **P2 — The promised factual review still depends on taste and has no binding composition record.** `.claude/skills/ios-design/REVIEW.md:7` asks what “competes,” where the eye starts/thumb rests, and whether a list would serve “better”; the tells add “too many,” “too much” and “dead space.” These have no shared pass boundary. Item 2 also demands top-leading placement even though `SKILL.md:39` explicitly permits a bottom-third hero. Step 4 accepts any “deliberate” explanation, so the original three equally prominent Start blocks can still pass by author assertion. Hand the reviewer the chosen job, state, wireframe/mock and explicitly accepted exceptions, then check the render against named relative size/fill/placement decisions. Keep aesthetic objections advisory and identifiable as judgments. This can make disagreements traceable; it cannot make design taste factual.

8. **P2 — The picker tell targets a legitimate iOS affordance.** `.claude/skills/ios-design/SKILL.md:106` treats “a picker that looks like a button” as control/content confusion. A picker is a control, and Apple's compact date picker and pull-down selection patterns intentionally use buttons. Start's `gymPicker` is a `Menu` (`StartWorkoutView.swift:328`) with a current value and chevrons. Its problematic prominence is distinct from the validity of its button affordance. Check that selection is distinguishable from the primary command, shows the current value and indicates disclosure; do not prohibit the native pattern. This is necessary to turn the reported Start failure into a reusable rule. [Apple pickers](https://developer.apple.com/design/human-interface-guidelines/pickers).

9. **P2 — The process ends before a completed independent review.** `.claude/skills/ios-design/SKILL.md:49` gives step 5 no completion criterion; step 7 (`:55`) ends at handing over a checklist, without requiring findings to return, corrections, renewed captures or re-review to clear. Steps 1–4 have stated bounds, but step 2's “obvious” and step 4's unrestricted justification remain subjective; step 6 needs the coverage definition above. Make step 5 end on implemented changes and the applicable documented gates, and step 7 end on a returned independent verdict with blocking findings resolved and fixes re-reviewed. That matches T6 and the actual ticket workflow. Passing gate-test counts in `REVIEW.md:30` does not establish that review itself finished.

10. **P3 — Universal composition rules reject useful patterns here.** `.claude/skills/ios-design/SKILL.md:42` requires every wireframe to fit one screen, although History and Exercises are unbounded collections. `REVIEW.md:9` likewise rejects any glanceable item below the fold. Require an initial viewport and explicit scrolling continuation instead. At `SKILL.md:63`, a single semantic item is not necessarily “a box around a sentence”: a workout/template or stat can have internal structure and warrant a card. Consistent radii across peer cards are also useful, despite the tell at `:98`; changing radius is not necessary to establish hierarchy. Scope these to redundant containers and competing treatment rather than cardinality or viewport length.

11. **P3 — Separate implemented token facts from new usage restrictions.** `.claude/skills/ios-design/REFERENCE.md:81` says `Hairline` is separators-only, while the shared `.card()` explicitly draws a Hairline border (`CardStyle.swift:13`). A faint border is not automatically an invisible or invalid border when the contrasting fill already defines the card. Prohibit relying on Hairline alone for an essential shape if that is the intended lesson; label separator-only as a proposed change if retained. The Unit token value cells at `REFERENCE.md:85` are empty: current values are `#97C7EE`, `#A8CDBF`, `#B8A1EE`. `Drop` (`#B8A1EE`) is missing. Include it or point to Theme as the full semantic inventory so the colour rules do not erase its meaning.

12. **P3 — The reference-app generalisation overstates what the memory disclaimer supports.** `.claude/skills/ios-design/SKILL.md:27` describes Fitness as three rings, but the ring count depends on Apple Watch pairing; without it there is only Move. Rings encode Move/Exercise/Stand goals, not one accent per workout activity type. The claim at `:32` that all these apps share one hero on every screen is an inference, not a verified app property. Retain the memory label and state the particular screen/state and lesson. Hevy's top-level Start Empty Workout is supported by its official documentation; no definite error established in the compact logging description. Strong's documentation confirms templates on Start Workout, but does not establish the exact current two-column composition; leave that explicitly unverified. [Apple activity rings](https://developer.apple.com/design/human-interface-guidelines/activity-rings), [Hevy workout tracking](https://www.hevyapp.com/features/track-workouts/), [Strong templates](https://help.strongapp.io/article/105-about-templates).
