# Decision Log

Decisions made during product discovery (2026-08-08 interview). Each entry: decision, and why. Locked decisions are reopened deliberately, not drifted away from — an agent that finds one inconvenient should surface the conflict, not silently work around it.

## Product

| # | Decision | Why |
|---|---|---|
| D1 | Layered history fallback: this machine → same model elsewhere → exercise, labeled | Strict machine-only starts every new machine cold; exercise-first reduces the differentiator to a tag. Fallback keeps honesty *and* usefulness. |
| D2 | Machine/gym optional; remembered per gym per exercise. (Refined by D19: equipment context lives on the entry, not per set) | Free weights, home workouts, and lazy logging must work; friction kills fast logging. |
| D3 | Seed equipment models only; gyms/machines always user-created | A worldwide gym database is impossible offline and its machine inventories are unknowable. Creating a gym takes 10 seconds, once. |
| D4 | Catalog depth: major brands, popular lines — **1877 models across 23 manufacturers** as shipped by ticket 20 (amended 2026-08-10; the original "~hundreds" was a placeholder written before the research existed). Depth is bounded by *verifiability*, not by a count: a model name ships only if it is traceable to the manufacturer's own listing or an authorised dealer carrying the manufacturer's SKU codes (`docs/catalog-sources/`), and a line whose members are not enumerated is not seeded at all. One real machine gets exactly one catalog UUID — near-duplicate identities are a generator error, not a curation preference | Covers most commercial gyms; long tail via user entry. A plausible-but-invented model is worse than an absent one, and a *duplicated* one is worse still: D23 keys history and records on the model UUID, so two rows for one machine split the user's own history (codex-review-4). The original rationale ("weeks of work for two people") was stale on both counts — the project is solo (D5) and the work was done by an agent in one session. |
| D5 | Audience: the developer alone (v1) | Cuts onboarding/dedup/polish scope. Stable IDs + export keep public release open. (Amended 2026-08-08: project is solo, not two-person.) |
| D6 | Templates are generic; resolved to last-used machine per gym at workout start | One "Push Day" works at every gym; gym-pinned templates break when traveling. |
| D7 | Models map to exercises; free weights are equipment tags, not machines | Machine pick auto-fills exercise (speed); multi-exercise stations prompt; barbells aren't machines. |
| D8 | PRs: per-rep-count bests + est. 1RM at machine/model/exercise layers | Heaviest-set-only is meaningless for machine training; mirrors the fallback layers. |
| D9 | Mixed units display as entered + convert toggle | Converting silently (90.7 kg for a 200 lb entry) is exactly the falseness the app rejects. **The ≈ marking of converted values was dropped 2026-09-04 by D52; the as-entered storage and the toggle stay.** |
| D10 | Log-time context snapshots; archive instead of delete; model corrections prompt past-vs-future | History must survive renames, re-modeling, and deletions without silently changing meaning. |
| D11 | Prefill from same-machine history only | Prefilling another machine's numbers would assert cross-machine comparability we reject. |
| D12 | Set types: warmup/working/failure; warmups excluded from PRs/volume | The minimal set that keeps records honest. RPE/supersets deferred. (Amended by D26: drop sets added.) |
| D13 | Rest timer: auto-start on completion, per-exercise durations (warmup vs. working split), notification | Strong-standard behavior; the split is a verified Strong nicety worth matching. |
| D14 | Load types: weighted / bodyweight / bodyweightPlus / assisted, direction-aware | Assisted machines invert "better" (less assistance wins); naive weight×reps produces wrong PRs. |
| D15 | Strength-only v1 (no duration/distance sets) | Single set shape is the biggest scope containment available. |
| D16 | v1 extras all in scope but sequenced: export → charts → Strong import → plate calc | Everything ships in v1, but a gym-usable build exists early (dogfooding from milestone 2). |
| D17 | e1RM: Brzycki, 12-rep record cap | Strong parity (verified from their docs); estimates degrade past 12 reps. |
| D18 | Adopt Strong's template-drift prompt (update/values-only/both/keep) | Elegant, proven solution to template drift. |
| D19 | Equipment context lives on ExerciseEntry and freezes once the entry's first set completes — permanently, even if that completion is later undone. Switching equipment starts a new entry; uncompleted draft rows move to it, completed sets stay | Prevents completed sets being silently relabeled; keeps snapshots, prefill, and machine PRs historically honest (2026-08-08 Codex cross-review, finding 2). **Reopened once, narrowly, by D51 (2026-09-04).** |
| D20 | e1RM is computed for `weighted` exercises only. Assisted records = least assistance per rep count; bodyweight+added = most added weight per rep count (athlete bodyweight intentionally ignored); plain bodyweight = most reps, uncapped. The D17 12-rep cap applies only to weight-keyed rep-count tables | Brzycki is mathematically invalid on inverted (assisted) or offset (bodyweight) loads (review finding 5). |
| D21 | Volume = Σ(normalizedKg × reps) over completed working+failure sets of `weighted` exercises. Dumbbells are logged as labeled (per hand) and never auto-doubled. Assisted/bodyweight excluded from volume in v1 | One consistent honest rule; resolves the deferred dumbbell question; avoids Strong's per-platform divergence (finding 14). |
| D22 | Rest-duration precedence: per-exercise override → global defaults (2:00 working / 1:00 warmup). Failure sets use the working duration. TemplateItem carries no rest duration in v1 | Single storage owner; documents the warmup default explicitly (finding 16). |
| D23 | Context snapshots store stable UUIDs (exercise, machine, model, gym), the exercise's **loadType**, and the **freeWeightTag**, alongside display strings; historical queries (prefill, layers, records) group by snapshot values, never live relationships | A "future-only" model correction or a catalog loadType edit must not reinterpret old sets (findings 3; pass-2 criticals 2–3). **Reopened once, narrowly, by D51 (2026-09-04): the dumbbell reclassification, with provenance on the row.** |
| D24 | Catalog seeding is versioned, idempotent reconciliation keyed by fixed catalog UUIDs. Mutable seeded fields are allowlisted (name, exercise links, metadata); seeded rows are not user-editable — only user-created models/exercises can be renamed | First-launch-only seeding would strand installs; unrestricted edits would fight reconciliation (finding 9; pass-2 important 8). **Amended 2026-08-25 (milestone 8, ticket 02), reopened deliberately rather than contradicted:** a seeded row's **`loadType`** IS user-editable, and the edit is marked with `Exercise.loadTypeUserOverridden` so reconciliation skips that one field and keeps owning every other allowlisted field. Naming stays reserved, as originally written. The reason for the exception: a wrong load type is not a naming preference — it ranks records in the wrong direction (assisted is lower-is-better), the user cannot avoid it, and the only other escape is logging against a different exercise, which splits their history (D23/D36). The override flag is what stops this fighting reconciliation, which is precisely what D24 was protecting against; it is exported (D28) so a restore cannot silently revert the correction. |
| D26 | **Drop sets are a fourth set type** (marker `D`), reopening D12's deferral at the user's request (2026-08-10). Semantics: a drop set is real work, so it counts toward records and volume exactly like a working or failure set — only warmups are excluded. Because a drop set is *by definition* performed without resting, completing one does **not** auto-start the rest timer (D13/D22 unchanged for the other three types). Prefill's type-aware index matching treats drop as its own sequence, consistent with how warmup and working already match. | The user logs drop sets in real training, so the app was silently unable to describe their actual workouts. Counting them toward records is the honest reading — the weight was lifted. Suppressing the timer encodes what makes a drop set a drop set, rather than nagging with a countdown the user will always skip. |
| D25 | Unit conversion uses exactly 1 lb = 0.45359237 kg; `normalizedKg` recomputes atomically on any value/unit edit; storage keeps full precision. Display: up to 2 decimals, trailing zeros trimmed, half-up rounding, locale-independent decimal point in storage; ~~converted values prefixed ≈~~ (dropped by D52, 2026-09-04) | Executable contract so normalized values can never drift from as-entered values (finding 12). |
| D27 | **Refines D24**: a user-created exercise may be linked to a *seeded* equipment model, and reconciliation **merges** rather than overwrites — a seeded model's `exerciseIDs` becomes the catalog's links (in catalog order) plus the user-added links to `isSeeded == false` exercises the store already held. Stale links to seeded exercises the catalog dropped are still removed. | Ticket 19 lets an unlisted movement be invented at the station it is performed on, and that station is usually a catalog model. `exerciseIDs` is an allowlisted seeded field, so a plain overwrite would silently unlink the user's exercise on the next catalog bump — D24 says reconciliation never touches user-created rows, and dropping a user's link is touching it. |
| D28 | **The export carries the user's data, not the shipped catalog.** Seeded exercises and equipment models appear only where the user's data references them (a machine's model, a history snapshot, a template item, a gym memory, a rest override); references are not followed transitively. The file records `seededCatalogVersion` so the omitted rows stay reproducible from the app itself. | A personal backup that is 1877 rows of someone else's catalog and one workout is not a backup of the user's training. The catalog ships in the binary and is versioned (D24); the user's history exists nowhere else. |
| D29 | **Exports carry weights as entered *and* normalized, never converted for display**: `weight`, `unit`, `weightKg`, at full precision. No `≈` value ever reaches a file. | The ≈ marker is a UI honesty device for a *converted* number (D9/D25). A file has room for both exact numbers, so it gets both — and a consumer never has to guess what unit a column is in, which is exactly Strong's failure (SPEC line 88). |
| D30 | **Nothing is silently dropped from an export.** Uncompleted draft sets, entries with no completed sets, and the workout still in progress all export, flagged (`completed`, empty `finishedAt`). Consumers filter as `RecordsMath` does. **Amended 2026-08-11 (codex-review):** the two files carry this differently — JSON is the complete backup; CSV is a complete ledger of *sets*, so a workout or entry holding no set at all has no row in it. A draft entry exports the equipment the user has chosen (live), since its D23 snapshot does not exist until the first set completes. | A backup that omits rows is not a backup; the omission is discovered when the data is needed. Flagging costs one column and keeps the file a faithful copy rather than an interpretation. "One row per set" has nowhere to put a setless object, so the claim is narrowed rather than left false. |
| D31 | **Export timestamps are ISO 8601 with the exporting device's UTC offset and fractional seconds** (`2026-08-11T18:30:00.123+09:00`). **Amended 2026-08-11 (codex-review):** filenames carry local wall time only (`workout-tracker-2026-08-11-1830`) — no offset, no sub-seconds. | A workout log is a record of local time-of-day; bare UTC would file a 6 a.m. Seoul session under the previous evening. Sub-seconds matter because `CanonicalRow` breaks duplicate-row ties on `updatedAt` before the id, so two updates in one second must stay distinct. A filename is for a human sorting files, and an offset in it buys ambiguity, not precision. |
| D32 | **CSV is RFC 4180 with CRLF and a UTF-8 BOM, and user text is written verbatim.** Fields containing quote/comma/CR/LF are quoted with inner quotes doubled; nothing is prefixed to defuse spreadsheet formulas. | The BOM is for Excel, which otherwise mojibakes non-ASCII gym names. Verbatim because the file's whole job is fidelity: rewriting a note that happens to start with `=` corrupts the user's own words to defend them from their own spreadsheet. |
| D33 | **A scanned name plate proposes a catalog model; the user confirms it.** The sheet shows the recognised text and the ranked candidates with scores, and always offers "none of these". Nothing is applied without a tap. A row is **preselected only when all three hold**: score ≥ 0.85, the plate names that row's manufacturer and no other known one, and the runner-up is ≥ 0.08 behind. Amended 2026-08-11 after the cross-review, which found four ways to preselect a wrong row on a score alone. | D23 keys history, prefill and PRs on the model UUID, so a confident wrong match splits the user's own history — the same damage duplicate catalog identities did (codex-review-4). Real plates are scuffed, angled and back-lit, and stablemates share most of their name: a Life Fitness Insignia chest press scores 100% while five siblings sit at 75–79%, so the *distinguishing* word is often the one a camera misses. |
| D34 | **A scan reads the photo and discards it.** No image is written to the store or to disk; only the recognised text (transient) and the model the user picks survive. | Keeping images would mean a schema change, storage that grows with every machine, a decision about whether exports carry pixels, and a CloudKit asset story — all to solve a problem the user did not have. Recognition is on-device (Vision), so no photograph of the user's gym leaves the phone. |
| D35 | **An unmatched scan creates a *user-space* model** (`isSeeded == false`), prefilled with the manufacturer in the catalog's canonical spelling when the brand is known, and the plate's most prominent non-junk line as the model name. Both fields stay editable before saving. | D4: a plausible-but-invented catalog row is worse than an absent one, so OCR output must never masquerade as seeded data. Canonical brand spelling keeps `LIFE FITNESS` from sorting as a different manufacturer than the 200 seeded `Life Fitness` rows, which is a real cost with no upside. |
| D36 | **A preset splits records.** PRs, e1RM, "previous performance" and prefill key on the preset alongside the equipment layers; the preset is part of the entry's D23 snapshot, and switching it on a frozen entry starts a new entry exactly as switching equipment does (D19). Volume, being a whole-workout number, still counts everything. | The user varies grip and single/double on the same machine (2026-08-12). Pooling them lets one variation set a "record" the other can never beat — the same falseness D1/D8 reject across machines, on the axis the user actually trains. A set already logged must never be relabelled into a variation it was not performed in. |
| D37 | **Presets belong to the exercise, not the machine.** "Seated Cable Row" offers its grips at every gym and on every machine; a machine may nominate which one it usually is. User-created only — nothing is seeded, though the add sheet suggests common names. | Same argument as D6's generic templates: a grip is a property of the movement and travels with the user, while retyping it per machine per gym is work with no payoff. A worldwide catalog of every grip on every machine is as unknowable as a worldwide gym database (D3). |
| D38 | **The preset is chosen at log time**, with the machine's usual one preselected and switchable in one tap. A stale machine default (deleted, or belonging to another exercise) degrades to "none chosen". | Grips vary session to session on one machine, so freezing the choice at machine-creation would mean editing the machine to change handles. Preselection removes the tap in the common case without deciding anything the user did not (D33's shape, one feature over). |
| D39 | **A bar is an input aid whose result is the total.** Wherever an entry is barbell work — the `barbell`/`smith` free-weight tags, or a machine whose catalog model is a rack or Smith — the user may pick a bar (a fixed list of standard bars, plus a custom weight); the weight field then takes the plates on **one** end and the app logs `bar + 2 × plates`. `SetRecord.weightValue` is the TOTAL in bar mode exactly as in total mode; the bar weight is stored alongside as provenance so history can show the breakdown and the next session can prefill plates rather than a total. The bar is **not** part of the D23 snapshot and not part of `RecordGroupKey`: changing bars does not split records the way changing equipment (D19) or variation (D36) does. | Two 135 lb sets are the same lift whether the number was typed or computed, so they must land in the same record table — the bar changes the *input*, not the load. And a stored weight that sometimes excluded the bar would silently drop every barbell PR by the weight of a bar with no error anywhere: `RecordsMath`, volume (D21), e1RM (D20) and the export's `weight` all read `weightValue` and know nothing about bars. The user asked for this on 2026-08-22; it is the first half of milestone 6's plate calculator (D16). |
| D40 | **A bar carries its own unit, and picking one sets the row's unit.** Bars are listed in kg and lb as *distinct* bars (a 20 kg bar is not a 45 lb bar), picking one never converts anything, and the kg/lb toggle is disabled while a bar is chosen. A row already carrying a total in the bar's own unit keeps it (the total is re-read as bar + plates); a total in the *other* unit is dropped rather than reinterpreted. | D9/D25 forbid silent conversion, and the toggle's own semantics — reinterpret the number in the other unit — would turn a 20 kg bar into a 20 kg-labelled 20 lb one on a stray tap. Switching unit means picking up a different bar, which is what happens in a gym. |

| D41 | **HealthKit and a watchOS companion are in scope** (2026-08-22), reopening SPEC's "No backend, accounts, **HealthKit**, **Watch**, or third-party runtime dependencies" at the user's explicit request. The rest of that sentence stands unchanged: no backend, no accounts, no third-party runtime dependencies, still fully offline. Live heart rate reaches the phone two ways — a `HKWorkoutSession` on the phone (AirPods Pro 3 and any heart-rate GATT wearable) and a watchOS companion streaming over `WCSession`, because the Apple Watch is **not** a GATT peripheral to the phone and cannot be read live without an app on the wrist. | The user asked for heart rate as a core feature, and every route to it is HealthKit. Verified before committing to it (2026-08-22): the **free** Apple account provisions `com.apple.developer.healthkit`, `.access` and `.background-delivery`, so this costs no Developer Program membership; the iPhone workout-session API is `ios(26.0)`; and the system, not the app, generates active energy during a session. Surfacing the conflict rather than drifting from it is what the preamble to this file requires. |
| D42 | **Minimum iOS rises from 17.0 to 26.0**, superseding SPEC's "iOS 17+". | `HKWorkoutSession`'s iPhone initialiser, `HKLiveWorkoutBuilder` and `HKLiveWorkoutDataSource` are all `API_AVAILABLE(ios(26.0))` — read from the SDK headers, not assumed. The app has exactly one user, whose phone runs 26.6, so availability-gating every heart-rate path would add branches that no device will ever take. |
| D43 | **A heart-rate rest ends on the threshold OR on a cap, and the alarm says which.** Per exercise the rest timer is standard (D13/D22) or heart-rate: rest ends when HR drops below a user-set bpm, or when a max-wait cap (default 4:00) expires. With no live source it degrades to the standard timer and says it degraded. | The cap is not decoration: one dropped connection, one bad sample, or one genuinely brutal set and a threshold-only rule waits forever — for an alarm whose whole job is to be the thing you do not have to watch. "You recovered" and "time is up" are different facts about the set you just did, so a notification that conflates them is lying about your training. |
| D44 | **The finish summary is HealthKit's numbers beside the app's own**: time, active calories, average and max HR, time in zones — plus total volume, the exercises performed, and their best sets. Heart-rate rows are **omitted, never zeroed**, when no session ran. The summary values are persisted on `Workout` rather than re-queried. | Apple's summary cannot say what you lifted; this app's cannot say what your heart did. The user asked for both on one screen. `0 BPM` for a workout logged without a sensor is not a missing value, it is a false one — the same distinction D30 draws for draft sets. Persisting mirrors D23: what History shows must not change because a source later changed its mind. |
| D45 | **An estimated maximum heart rate is marked as estimated wherever it reaches a screen** (~~on screen~~ — dropped by D52, 2026-09-04; the flag lives on in the data), until the user supplies a measured one. Zones are **55/65/75/85/95%** of max (revised 2026-08-24 — see below); with neither a measured max nor a birth date, zones are not shown at all. | 220−age carries a standard deviation of ±10–12 bpm, so an unmarked "Zone 4" asserts a precision the number does not have — exactly what D9/D25's `≈` exists to prevent one domain over. Showing no zone is honest; showing a confident wrong one is not. **Corollary, learned 2026-08-24:** a decision to hide a feature until the user supplies a basis is only honest if supplying that basis is REACHABLE. As shipped, the only way in was a button that rendered only once zones already worked, so no user could ever switch them on. Any new "hidden until configured" gate must ship its own way in — Settings, not just a contextual hint. **Boundaries revised 2026-08-24, deliberately reopening the 50/60/70/80/90 half of this decision:** after real gym use the user reported every zone reading about one too high, and chose to shift each boundary up 5 percentage points. Root cause is probably not the boundaries but the basis — they are on the 220−age estimate, which runs low for fit people, and a low max inflates every percentage. Raising the max was offered and declined in favour of the shift. **The cost, which is real: this app's "Zone 3" is no longer Polar's or Apple's Zone 3.** Zone names here are not portable, and a measured maximum would let these go back to standard. |
| D46 | **Anything that must happen at a moment in time while the app is backgrounded is SCHEDULED IN ADVANCE with the system, never executed by the app at that moment.** The rest-end beep is a pre-rendered `[silence][beep]` audio track handed to the audio pipeline when the rest starts; the rest notification is a `UNTimeIntervalNotificationTrigger`. Neither needs the app alive at the deadline. | iOS promises a backgrounded app no CPU at a chosen instant, so "run code when the timer ends" is built on something the platform does not offer. Three shipped builds of the audible rest alarm failed this way before the design changed (2026-08-25). A corollary that cost two of those builds: **a scheduled notification firing is NOT evidence the app was running** — the system owns that deadline. Early heart-rate recovery is the one ending that cannot be pre-scheduled, because its moment is genuinely unknowable in advance; it degrades to the queued cap alarm rather than to silence. |
| D47 | **History is editable, but only its numbers — and every edit is marked.** Correcting a logged set's weight/reps/type is legitimate; an edit must NEVER re-resolve the entry's frozen snapshot (exercise name, machine, gym, load type), and the workout is stamped `historyEditedAt`. Deleting a workout names what it destroys — sets, exercises, volume — before it happens. | Reopens the *spirit* of D23 deliberately rather than drifting from it. D23 froze history so the past could not be **silently** rewritten by today's catalog; a deliberate correction is a different act from unnoticed drift. The boundary is the whole decision: if an edit re-resolved snapshots, fixing a weight typo on a March set would restate that row with the machine's current name and the exercise's current load type — so re-tagging a supported dip today would silently re-rank every March set, with nothing on screen to say so. Marking edits is D9/D25's honesty rule: an unmarked alteration claims a certainty the log does not have. **Amended 2026-08-26 (codex-review 2, critical), reopening this decision rather than contradicting it:** ONE frozen field is user-correctable — an entry's `snapshotLoadType`, via `HistoryEditing.retype`. Everything else stays frozen: identity, machine, gym and names. The reason is that D47 as first written left the user's original complaint unfixable — a supported dip logged as `weighted` ranked heaviest-wins forever, correcting the exercise only affects future sets, and switching exercises splits history (D23/D36). The narrowness is the safeguard: one entry the user names on that workout's own screen, never a bulk sweep over history, never a change of identity, and marked as an edit like any other. A re-type that would strand a set the new type cannot express is refused (A1). **Amended again 2026-09-03 by D50:** a workout's user-typed NAME is the second editable non-number, for the reasons given there. **D51 (2026-09-04) is different in kind — a catalog-driven reclassification with its own provenance fields, not a marked user edit; see there.** |
| D48 | **A superset is a group of adjacent exercise ENTRIES (`ExerciseEntry.supersetGroupID`), and rest is taken after the LAST member, not between members.** Grouping is presentation and rest behaviour only: records, PRs and volume for a set inside a superset are identical to the same set logged alone. | Reopens SPEC's post-v1 deferral of "RPE/supersets" deliberately, at the user's request (2026-08-25), who also chose both halves. Entries rather than a set-level tag because that is how the technique is actually performed — A1/B1, A2/B2, alternating — and a tag would record that sets were "in a superset" without modelling the alternation that makes it one. Rest after the last member because moving straight from A to B with no rest IS the technique; a timer firing between them would tell the user to do the opposite of what they chose. The invariant matters most: if grouping altered records, every PR would depend on how the user happened to arrange that day's workout, and the records would stop meaning anything. Grouping is by ADJACENCY, not by id alone — ordering is what the user can see, so an interrupted group renders as two runs rather than pretending the interruption did not happen. |
| D49 | **Strong CSV import is dropped from v1, reversing D16.** The importer is not built and is not planned; SPEC keeps the format analysis (no unit column, no workout id, set tags lost, equipment in the name suffix) as a record, since that analysis is the hard part and survives the decision. Reopen this only if a real Strong export appears. | The user has no Strong history to import (2026-08-29), so the whole milestone would move zero rows — every hazard in the format is a cost with no matching benefit. D16 sequenced it into v1 back when the assumption was that history existed to migrate; that premise was never checked with the user and turned out to be false. **Recorded here late:** the drop was made and written into SPEC/STATE on 2026-08-29 WITHOUT reopening D16, which CLAUDE.md requires for a locked decision; a Codex cross-review caught the omission the same day. |
| D50 | **A workout's name is the user's label, editable in History as a marked edit — reopening D47's "only its numbers" for this one field.** `Workout.name` is optional; nil means nothing was typed and the title derives from the template snapshot, else the exercises, exactly as before. Naming a RUNNING workout is just typing (`WorkoutSession.rename`, unmarked, refuses a finished workout); renaming LOGGED history (`HistoryEditing.rename`) stamps `historyEditedAt` like every other edit and refuses a running one. Export carries it as a new field/column beside `sourceTemplateName`, never in its place. | The user asked to name workouts mid-session and afterwards (2026-09-03). D47's boundary exists to stop a correction from re-resolving something the app CAPTURED — a machine, a gym, a load type — so that March's rows keep saying what March meant. A name is not captured; it is authored, stored on the workout itself, and nothing downstream reads it: records, charts, prefill, volume and drift detection are all indifferent to it. So editing it cannot re-rank or re-label a single set, which is the harm D47 guards against. What it CAN do is make a workout claim to have always been called something it was not — which is why it is marked, and why the running/logged split is enforced in the Domain rather than left to whichever screen calls. `sourceTemplateName` is untouched: provenance and intent are different facts and the export keeps both (codex-review 02 caught a first cut that merged them into one CSV column). |
| D51 | **One catalog-driven reclassification of frozen snapshots — dumbbell-tagged sets of a barbell/machine movement become that movement's dumbbell exercise — reopening D19/D23/D47 for exactly this, on these terms.** (1) Not a user edit: `historyEditedAt` is NOT set; instead the row carries `reclassifiedAt` + `reclassifiedFromExerciseName`, exported (schema 7) and shown in History. (2) Narrow: finished workouts, frozen snapshots whose tag is Dumbbell, movements listed in `DumbbellCounterparts` (by catalog UUID); Deadlift, Squat and Preacher Curl are deliberately unmapped. (3) The variation moves with the movement: the entry's preset is re-homed to a same-named preset on the counterpart, relationship AND `snapshotPresetID`. (4) Runs on every launch from catalog version 5, gated by one count query, idempotent because no target is a source; the first run and every moving run are recorded on `AppPreferences` and Settings shows the count. (5) Mid-workout, the equipment sheet offers the counterpart exercise instead of the Dumbbell tag, so the old shape cannot re-grow. | The user did a dumbbell bench and said so with the tag; the catalog had no row for it, so the identity was the catalog's gap, not the user's error — which is why it is corrected by the catalog and marked as provenance rather than as an edit. D19/D23 exist so that TODAY's definitions cannot silently restate what MARCH meant; this restates March in March's own terms, with what it said before kept on the row. Presets must move because their UUID is record identity (D36) and they belong to one exercise (D37): left behind, migrated history would be an island no future set could join. A one-shot version gate was rejected because history arrives after crossings (merges, restores) and would be missed forever. codex-review 04 found the first cut wrong on all of these — unmarked, preset-stranding, one-shot, unexported — and this decision is the corrected design, not a rationalisation of the first one. |

## Technical

| # | Decision | Why |
|---|---|---|
| T1 | SwiftData | First-party, SwiftUI-native, fits no-dependency rule. Weak migrations mitigated by simple models + denormalized snapshots. |
| T2 | CloudKit-compatible schema; ship single-device | UUIDs/optional relationships/no unique constraints cost little now; retrofitting sync later is a painful migration. |
| T3 | UI-first build order | User requirement: see and approve the screens (sample data) before logic/persistence is wired. |
| T4 | Xcode buildable folders (synchronized groups) | Adding files doesn't touch project.pbxproj — no merge hazard, and agents can add source files without editing project config. |
| T5 | Repo is the source of truth for spec/context | Any agent session (Claude Code or Codex, either dev) loads identical context from docs/. |
| T6 | Cross-review over double-build | Work is reviewed by a **different agent than the one that wrote it** (Claude ↔ Codex), against the tickets and this decision log. Solo development means this is the only independent check that exists — it is not optional ceremony. Proven 2026-08-08: a Codex review of Codex-written code plus a Claude review of it caught 9 real defects, 3 of which broke the product's historical-honesty thesis. Codex may also independently author adversarial tests for the pure-logic core against the spec. |
| T7 | Unit-default precedence: machine → gym → app preference | Most specific context wins. |
